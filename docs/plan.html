Axiom WorldEdit GUI

Открытый Fabric-аддон для Axiom 6.1.5, который даёт доступ ко всему WorldEdit 7.4.6 из редактора Axiom в одиночной игре: меню, окна, инструменты, редакторы паттернов и масок, общий журнал отмены. Здесь собраны список функций обоих модов, сравнение, архитектура и план работ. Кода пока нет.

Коротко: что я рекомендую

  1. Вызывать WorldEdit напрямую на встроенном сервере через общий интерфейс WeBackend. Команда разбирается самим WE, а вывод перехватывает свой Actor, поэтому чат не засоряется. Это даёт точную форму выделения Axiom и общий буфер обмена. Отправка команд от игрока остаётся запасным вариантом, если позже понадобятся серверы.
  2. Один журнал отмены — журнал Axiom. Каждая операция WE записывается в историю Axiom как отдельный шаг, а в историю WE не попадает. Ctrl+Z, Ctrl+Y и окно History отменяют правки Axiom и WE в общем порядке.
  3. Главное выделение — выделение Axiom, синхронизация в обе стороны. Axiom → WE через свой RegionSelector с точной формой. WE → Axiom через пакеты CUI-протокола: он вложен в сам WorldEdit, поэтому WorldEditCUI не нужен. Рисует выделение Axiom.
  4. UI встраивать миксинами: пункт «WorldEdit» в MainMenuBar.render() и свои ImGui-окна в цикле отрисовки EditorUI. Кисти WE сделать инструментами Axiom через официальный ToolRegistryService из axiomclientapi.
  5. Формы строить по схеме команд, которую я извлёк из аннотаций @Command, @Arg и @Switch: 174 команд с аргументами, значениями по умолчанию и флагами. Для самых частых команд сделать отдельные окна вручную.
  6. Паттерн и маска хранятся строкой WE, а визуальный редактор её собирает: блоки из палитры Axiom, веса в процентах, теги, состояния. Проверку и подсказки даёт сам WE через PatternFactory и MaskFactory.

В дампе потоков кода аддона нет: клиент ждёт задачу от уже остановленного сервера, а в логе каждый раз предупреждение FastQuit «was not registered in currently saving worlds». В сборке стоит fastquit-3.1.5+mc26.2, собранный под 26.2. Мир к моменту зависания сохранён.

4.1. Как GUI вызывает WorldEdit

Прямой вызов API основа

Одиночная игра. В server.execute() вызывается PlatformCommandManager.handleCommand(new CommandEvent(actor, "//set …")) со своим Actor, который перехватывает вывод.

  • Доступны все 174 команд: аргументы разбирает сам WE
  • Структурированные ответы и ошибки без чата
  • Доступ к LocalSession: буфер обмена, маска, кисти
  • Свой RegionSelector с точной формой выделения Axiom
  • Перехват истории WE для общего журнала (4.5)

Команды от игрока на потом

Форма собирает строку, и мод отправляет её через connection.sendCommand("/set 30%stone,dirt").

  • Нужно только для серверов: там WE в другом процессе
  • Ответ приходит текстом в чат, выделение передаётся только рамкой, общего журнала нет

Своя реализация операций

Переписать логику WE на клиенте и отправлять блоки пакетами Axiom.

  • Огромный объём, расходится с WE при каждом обновлении
  • Не рекомендую

Решение. Все вызовы идут через интерфейс WeBackend. Сейчас у него одна реализация, DirectBackend. Если позже понадобятся серверы, рядом появится CommandBackend, а окна и инструменты менять не придётся. Команда выполняется в потоке сервера, результат возвращается в поток клиента через Minecraft.execute().

interface WeBackend {
  CompletableFuture<WeResult> run(String command);      // "//set stone" → сообщения, ошибки, число блоков
  void pushSelection(AxiomSelectionSnapshot sel);        // Axiom → WE
  CompletableFuture<List<String>> suggest(String partial); // подсказки WE
  Optional<String> validatePattern(String input);         // ошибка разбора или пусто
}

4.2. Выделение

Выделение Axiom главное рекомендую

  • Axiom → WE. Перед каждой командой в сессию WE ставится свой RegionSelector. Для SelectionBuffer.AABB он отдаёт обычный CuboidRegion, поэтому работают и команды, которым нужен именно кубоид (//line, //stack). Для произвольного набора (magic, lasso) он отдаёт свой Region по вокселям Axiom с точной формой. Если команде нужен кубоид, а выделение произвольное, она получает рамку с предупреждением.
  • WE → Axiom. Обработчик CUIPacketHandler.instance().registerClientboundHandler(...) из протокола, вложенного в WE. События s, p, mm, e, cyl, poly собирают форму. Cuboid превращается в Selection.addAABB, остальные формы растеризуются в PositionSet с лимитом объёма.
  • Защита от петли: у каждого изменения есть источник, и эхо своих же изменений игнорируется.
  • Если WorldEditCUI нет, мод сам отправляет рукопожатие CUIPacket("v", "4"), чтобы сервер начал слать события.

Интеграция с WorldEditCUI

  • Рисует настоящие формы WE: полигоны, эллипсоиды, сетку
  • Но это второй визуальный слой поверх Axiom и чужой API без контракта (CUISelectionProvider)
  • Сам протокол доступен и без WorldEditCUI

Рекомендация. Согласен с твоим выбором: выделение Axiom, его HUD и отрисовка. WorldEditCUI не нужен как зависимость. Если он установлен, лучше скрывать его рамку, пока открыт редактор Axiom, чтобы не было двух рамок. Типы WE, которых нет в Axiom (poly, ellipsoid, cyl, convex), задаются в окне «Выделение WE» полями и кликами. После команды Axiom показывает их как воксельное выделение.

4.3. Как встроить UI

Меню и окна миксинами

  • @Inject в MainMenuBar.render() перед вызовом ImGui.endMainMenuBar() (remap = false): верхнее меню «WorldEdit» с подменю по группам
  • @Inject в цикл EditorUI после ImageReferenceWindows.render(): свой менеджер окон на ImGui Axiom (imgui.moulberry92) с докингом и сохранением открытых окон в своём конфиге
  • Виджеты Axiom берутся из ImGuiHelper.blockStateButton и SelectBlockWidget

Кисти через axiomclientapi

  • В редакторе Axiom игрок в режиме спектатора, поэтому кисти WE, привязанные к предмету, не срабатывают
  • Каждая кисть WE становится CustomTool через ToolRegistryService, подключённый в META-INF/services: это публичный API, и он стабильнее внутренностей
  • Клик даёт точку из ToolService.raycastBlock(), и кисть выполняется через бэкенд
  • Если API не хватит для превью и опций, используется ToolManager.addTool(Tool)

Рекомендация. Сделать оба варианта. Меню и окна — для операций над выделением, кисти — для работы кликом. Окна:

  • Командная палитра: поиск по всем 174 командам с формой из схемы
  • Регион, Генерация, Выделение WE, Буфер и схематики, Биомы, Снапшоты
  • Сессия: gmask, limit, timeout, perf
  • Консоль WE: ответы и ошибки, кнопки WE Undo и Redo

Формы строятся из схемы автоматически: Pattern и Mask получают редактор паттернов, числа — поля со слайдером, BlockVector3 и направления — выбор направления (me, up, north…), enum — выпадающий список, флаги — чекбоксы.

Кисть строится как Brush WE и применяется к точке клика через brush.build(editSession, position, pattern, size). Каждый мазок становится шагом общего журнала.

4.4. Паттерны и маски в UI

Редактор паттерна

  • Источник истины — строка WE, а визуальный список её собирает и разбирает
  • Строка списка: кнопка блока из blockStateButton, вес в процентах, модификатор (* случайное состояние, ^ применить)
  • Быстрые вставки: активный блок и палитра Axiom, ##тег, #clipboard@[x,y,z]
  • Полоса весов показывает доли блоков

Редактор маски

  • Чипы, которые соединяются по И: блоки, !, #existing, #solid, #surface, #region, $биом, %шум, >, <, ~, =выражение
  • Кнопка «Взять из Axiom Tool Masks»: перевод через CmdStringConverter. block, above, below, adjacent, biome, coord и НЕ переводятся; angle, near, can see sky, Lua и общее ИЛИ — нет, они подсвечиваются
  • «Сделать глобальной» отправляет //gmask

Проверка и подсказки

  • Разбор через WorldEdit.getPatternFactory() и getMaskFactory() на каждое изменение поля, с точной ошибкой
  • Подсказки из getSuggestions() тех же фабрик: блоки, теги, биомы
  • Выражения: подсветка переменных и функций, пресеты для //generate

4.5. Общий журнал отмены

Без него у Axiom и WE две истории, и они не знают друг о друге. Запись истории Axiom (HistoryEntry) хранит снимки блоков «до» и «после», а Ctrl+Z просто записывает в мир снимок «до». Пример: Fill камнем в Axiom, затем //overlay grass в WE поверх, затем Ctrl+Z. Axiom вернёт снимок «до Fill» и сотрёт траву WE внутри области. После этого //undo WE вернёт камень пятнами.

Как устроено решено

  • Миксин в LocalSession.remember(EditSession): когда WE хочет запомнить операцию, аддон забирает её ChangeSet
  • Каждое изменение BlockChange(position, previous, current) раскладывается в два BlockBuffer Axiom: «до» и «после». Блоки с данными идут как CompressedBlockEntity, биомы — в BiomeBuffer
  • Запись «WE: //overlay (1 234 блока)» добавляется в Dispatcher.history через миксин-аксессор. Публичный Dispatcher.push() не подходит: он заново применяет блоки «после»
  • В историю WE такая операция не попадает, поэтому второго журнала нет
  • Так перехватываются и команды, набранные в чате, и мазки кистей WE

Что остаётся в //undo WE

  • Операции, в ChangeSet которых есть сущности (EntityCreate, EntityRemove): /butcher, /remove, //paste -e, //copy -e с переносом
  • Их запись в Axiom не делается целиком, иначе отмена вернула бы блоки, но не мобов
  • В консоли аддона и в окне такая операция помечается «отмена только через WE Undo»

Что проверить на этапе 1. Порядок записи, когда операция WE идёт сразу после незавершённой правки Axiom (applyPendingHistory). Сохранение журнала на диск через HistoryIO для больших операций. Память: ChangeSet WE и запись Axiom не должны жить одновременно дольше, чем нужно для переноса.

Вопросы перед стартом

Решено: только одиночная игра, общий журнал Axiom, open source под GPL-3.0. Произвольное выделение передаётся точной формой. Остались вопросы:

  1. WorldEditCUI: скрывать его рамку в редакторе Axiom, оставить или ты его удалишь?По умолчанию: скрывать, пока открыт редактор.
  2. Состав MVP: подходит список команд из этапа 1 или чего-то не хватает?По умолчанию: список из этапа 1.
  3. Язык интерфейса: русский, английский или оба?По умолчанию: оба, через lang-файлы.
  4. Писать в общий журнал и команды WE, набранные в чате, или только операции из окон аддона?По умолчанию: все операции WE, чтобы Ctrl+Z работал одинаково.
